# T1543.002 - Systemd Service Persistence

| Field | Value |
|---|---|
| ATT&CK | T1543.002 - Create or Modify System Process: systemd service |
| Tactic | Persistence |
| Data source | Sysmon EID 1 (ProcessCreate); auditd (file write) |
| Severity | High |
| Status | validated |

## Hypothesis
Persistence via a malicious systemd unit requires either writing a `.service` file under
`/etc/systemd/system/` or registering it with `systemctl enable` + `daemon-reload`. This
lab's Sysmon config does not watch `/etc/systemd/`, so we detect the ACTION (`systemctl
enable`) rather than the file. This is a real lesson: your detection surface is bounded by
your sensor config - know what yours covers.

## Detection (SPL)
```
index=soclab sourcetype=linux:sysmon
| rex field=_raw "<EventID>(?<eid>\d+)"
| rex field=_raw "<Data Name=\"CommandLine\">(?<cmd>[^<]+)"
| rex field=_raw "<Data Name=\"User\">(?<user>[^<]+)"
| where eid=1 AND match(cmd,"systemctl (enable|daemon-reload)") AND NOT match(cmd,"--user")
| table _time user cmd
```

## Known limitations
- `systemctl enable` of a LEGITIMATE new service (installing real software) also fires -
  in production, correlate with the .service file's path/signature or scope to off-hours.
- An attacker using a systemd *user* unit or a `.timer` evades the `--user` exclusion and
  the `enable` keyword respectively - extend the match for full coverage.
- Best production version watches the file write directly (add `/etc/systemd/system` to the
  Sysmon FileCreate include list, then detect on EID 11 like the cron rule).
