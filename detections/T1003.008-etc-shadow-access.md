# T1003.008 - Credential Access via /etc/shadow

| Field | Value |
|---|---|
| ATT&CK | T1003.008 - OS Credential Dumping: /etc/passwd and /etc/shadow |
| Tactic | Credential Access |
| Data source | Falco (primary), auditd (corroborating) |
| Severity | High |
| Status | validated |

## Hypothesis
`/etc/shadow` holds password hashes and is read by a very small, enumerable set of
legitimate processes (PAM during auth, `unix_chkpwd`, `passwd`, backup agents). Any
*other* process reading it - `cat`, `cp`, a scripting interpreter, a compiled tool -
is a strong credential-access signal. The benign population is small enough to alert on
directly, which is exactly why this is a good first detection.

## Detection (SPL)
Falco already ships a rule for this ("Read sensitive file untrusted"). We ingest Falco's
JSON and alert on it, then corroborate with auditd for the process lineage.

```
index=soclab sourcetype=falco:json
| spath output_fields.fd.name output=file
| where file="/etc/shadow"
| spath output_fields.proc.pname output=parent
| spath output_fields.proc.name  output=proc
| spath output_fields.user.name  output=user
| stats count min(_time) as first max(_time) as last
        values(parent) as parent values(user) as user by proc
| convert ctime(first) ctime(last)
```

Corroborate / pivot in auditd (raw open on the shadow inode):
```
index=soclab sourcetype=linux:audit "/etc/shadow" type=SYSCALL
| stats count values(exe) as exe values(comm) as comm by pid, auid
```

## Tuning log
Observed on the confirmed live event during build-out:
`cat /etc/shadow` with lineage `cat <- sudo <- bash <- sshd`, user root, loginuid 1000.

| Date | Benign source that fired | Decision | Rationale |
|------|--------------------------|----------|-----------|
| build | `unix_chkpwd` (PAM auth path) | exclude | Signed system binary, fixed path, fires on every login by design |
| build | `sshd`/`systemd` direct reads | keep watch | Rare; if seen without a login event, investigate |

## Known limitations
- An attacker reading the file via a **renamed** copy of `cat` still fires (rule keys on
  the target file, not the tool) - good. But reading it via a **kernel-level** primitive
  or a memory-mapped approach that bypasses `openat` would not appear in either sensor.
- Reading `/etc/shadow.bak` or a backup copy elsewhere is not caught - the rule is scoped
  to the canonical path. A production version would add the backup paths.
