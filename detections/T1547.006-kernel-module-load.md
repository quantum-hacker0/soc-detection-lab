# T1547.006 - Kernel Module Load (LKM)

| Field | Value |
|---|---|
| ATT&CK | T1547.006 - Boot or Logon Autostart: Kernel Modules and Extensions |
| Tactic | Persistence / Privilege Escalation |
| Data source | auditd (init_module / finit_module syscalls) |
| Severity | High |
| Status | validated |

## Hypothesis
Loading a kernel module is how rootkits install. On a running production server, modules
are loaded at boot and essentially never during steady-state runtime. A module load by an
interactive user (auid != -1) mid-session is a strong signal. This lives in auditd, not
Sysmon - a reminder that different techniques need different sensors.

## Detection (SPL)
```
index=soclab sourcetype=linux:audit (syscall=313 OR syscall=175)
| rex "comm=\"(?<comm>[^\"]+)\""
| rex "auid=(?<auid>\d+)"
| table _time auid comm syscall
```
(syscall 175 = init_module, 313 = finit_module - the two ways to load a module.)

## Tuning log
| Date | Benign source that fired | Decision | Rationale |
|------|--------------------------|----------|-----------|
| build | (none at runtime) | none needed | modules load at boot; baseline captured no runtime loads |
| note | boot-time module loads have auid=4294967295 (unset) | in prod, filter to `auid<1000`-set (a real user) | separates interactive loads from boot |

## Known limitations
- Legitimate admin actions (loading a driver, `modprobe` for hardware) also fire - scope to
  unexpected module names or off-hours, and alert at low severity for expected admin work.
- A rootkit that loads via a boot-time mechanism (initramfs, /etc/modules) won't show a
  runtime syscall - pair with file-integrity monitoring on module config paths.
