# T1070.003 - Clear Command History / Logs

| Field | Value |
|---|---|
| ATT&CK | T1070.003 - Indicator Removal: Clear Command History (and logs) |
| Tactic | Defense Evasion |
| Data source | auditd (EXECVE) |
| Severity | Medium |
| Status | validated (with a documented blind spot) |

## Hypothesis
Attackers cover tracks by deleting or truncating logs and shell history. Deletion in
general is far too noisy to alert on (systemd/sshd delete temp files constantly - the
baseline `key=delete` count is dominated by benign activity). The tractable signal is a
delete/truncate tool targeting a LOG file or history file specifically.

## Detection (SPL)
```
index=soclab sourcetype=linux:audit type=EXECVE
| rex "a0=\"?(?<a0>[^\" ]+)"
| rex "a1=\"?(?<a1>[^\" ]+)"
| rex "a2=\"?(?<a2>[^\" ]+)"
| where match(a0,"(rm|shred|truncate|unlink)$")
    AND (match(a1,"(var/log|wtmp|btmp|lastlog|bash_history)")
      OR match(a2,"(var/log|wtmp|btmp|lastlog|bash_history)"))
| table _time a0 a1 a2
```

## Tuning log
| Date | Benign source that fired | Decision | Rationale |
|------|--------------------------|----------|-----------|
| build | generic `key=delete` (systemd/sshd temp files, 60+) | DID NOT use it - too noisy | deletion alone is not a detection |
| build | narrowed to delete-tool + log-path | 0 in baseline | admins rarely rm a log file interactively |

## Validation
- [x] Fires on: truncate of `/var/log/*` - 2 rows (were the lab's own log resets, which
      correctly demonstrate the rule detects log truncation)
- [x] Silent on: `index=soclab_baseline` - 0 rows
- [x] FP count on baseline after tuning: 0

## Known limitations (READ THIS - it's the honest part)
- **`history -c` is a genuine blind spot.** It is a bash BUILTIN: no process is spawned and
  no syscall is issued, so neither Sysmon nor auditd sees it. To detect history tampering
  you must add an explicit auditd WATCH on the history file
  (`auditctl -w /home/analyst/.bash_history -p wa -k histfile`) - a sensor-config change,
  not a rule change. Stating this gap is more valuable than pretending the rule catches it.
- `cat /dev/null > ~/.bash_history` also evades this rule (the redirect truncates without
  rm/shred/truncate) - same fix: watch the history file directly.
- An attacker who edits a log in place (removing only their lines) does not delete it -
  needs log-integrity/hashing, out of scope for exec-based detection.
